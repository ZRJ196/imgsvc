# 二、POST /infer 请求时序

## 2.1 完整时序（Mermaid）

```mermaid
sequenceDiagram
    autonumber
    participant B as 浏览器
    participant S as server.cpp
    participant P as preprocess
    participant I as InferEngine
    participant O as postprocess
    participant H as hash
    participant D as Db
    participant M as MySQL

    B->>S: TCP 三次握手（内核完成）
    S->>S: accept 返回 conn_fd（阻塞等待）
    S->>S: setsockopt SO_RCVTIMEO = 5 秒

    Note over B,S: ① 收请求头
    loop 直到找到 CRLF CRLF
        B->>S: recv 请求头
    end
    S->>S: sscanf 解析 method / path
    S->>S: find_ci 解析 Content-Length

    Note over B,S: ② 收 body（可能分多次到达）
    loop 直到 body 字节数达到 Content-Length
        B->>S: recv body
    end
    Note over S: body 就是图片原始字节

    Note over S,M: ③ 推理流水线（计时开始）
    S->>P: preprocess_bytes bytes
    P->>P: imdecode 得到 cv::Mat
    P->>P: blobFromImage resize 320x320 + BGR 转 RGB + 除以 255 + HWC 转 NCHW
    P->>P: 逐通道做 (x - mean) / std
    P-->>S: blob [1,3,320,320] CV_32F

    S->>I: run blob
    I->>I: CreateTensor（零拷贝，指向 blob 内存）
    I->>I: Session::Run（ONNX Runtime 内部推理）
    I->>I: mask.assign 拷贝输出（避免悬垂指针）
    I-->>S: mask 320x320，值域 0~1

    S->>O: make_cutout_png orig + mask
    O->>O: resize 掩码到原图尺寸
    O->>O: convertTo CV_8U（乘 255）
    O->>O: split BGR + push alpha + merge BGRA
    O->>O: imencode 编码成 PNG 字节
    O-->>S: png bytes
    Note over S,M: 计时结束，得到 cost_ms

    Note over S,M: ④ 记录入库
    S->>H: sha256_hex bytes
    H-->>S: 64 位十六进制 hash
    S->>D: log_infer name + hash + w + h + cost_ms
    D->>D: mysql_real_escape_string 转义
    D->>M: INSERT INTO infer_log
    M-->>D: OK
    D-->>S: true

    Note over B,S: ⑤ 响应
    S->>B: send_response 200 OK + image/png（send_all 循环写）
    B->>B: resp.blob 得到 Blob
    B->>B: URL.createObjectURL 显示结果
    S->>S: close conn_fd
```

## 2.3 关键点标注

| 阶段 | 关键细节 | 对应坑 |
|---|---|---|
| ① 收请求头 | 必须**循环** recv 直到出现 `\r\n\r\n`，因为头也可能分多次到达 | 短读 |
| ② 收 body | **第一次 recv 可能已经把一部分 body 一起收进来了**，所以要算"已收到多少、还差多少" | 短读 + 边界计算 |
| ② 收 body | 上限 10 MB，超过返回 **413** | 内存耗尽攻击 |
| ③ 预处理 | `imdecode` 失败返回空 Mat（不抛异常） | C 风格错误 |
| ③ 推理 | `CreateTensor` **零拷贝**指向 blob，所以 blob 必须活到 `Run` 结束 | 悬垂指针 |
| ③ 推理 | `mask.assign` 必须**拷贝**，否则 `outputs` 析构后指针悬垂 | 悬垂指针 |
| ④ 入库 | 文件名来自客户端，**必须转义** | SQL 注入 |
| ⑤ 响应 | `send_all` **循环写**，大 PNG 一次发不完 | 短写 |
| ⑤ 响应 | `MSG_NOSIGNAL` 防止 SIGPIPE | 进程静默死亡 |

```
 └────────┬─────────┘

          ▼

 └────────┬─────────┘
          │ split(BGR) + push_back(mask8) + merge
          ▼
 ┌──────────────────┐
 │  rgba            │  1245 × 843 × 4，CV_8U（BGRA）

          ▼
```

**为什么每一步都要清楚形状？** 因为**任何一步的形状错了，都不会报错，只会出垃圾结果**。
实测校验方式：预处理后打印 `min/max`，理论值域 `[-2.118, 2.640]`，精确命中即正确。

## 5.2 为什么要两个入口

| 用途 | 说明 |
|---|---|
| **调试** | 模块出问题时，不经过网络层直接复现，省掉 HTTP 干扰 |
| **交叉验证** | 同一张图，CLI 与 HTTP 输出 **SHA-256 完全一致** → 证明模块化重构没有改变行为 |
| **性能基准** | CLI 测纯计算耗时（不含网络），与服务器耗时相减可算出各层开销 |

# 六、连接生命周期

## 6.1 状态图（Mermaid）

```mermaid
stateDiagram-v2
    [*] --> 等待连接
    等待连接 --> 已连接: accept 返回 conn_fd
    已连接 --> 收请求头: 设置 SO_RCVTIMEO
    收请求头 --> 收请求头: recv 未找到 CRLF CRLF
    收请求头 --> 收body: 找到 CRLF CRLF
    收请求头 --> 关闭: 超时 / 断开 → 返回 400

    收body --> 处理: 收满
```

# 七、GET / 静态文件时序（对比）

```mermaid
sequenceDiagram
    autonumber
    participant B as 浏览器
    participant S as server.cpp
    participant SP as safe_path
    participant FS as 文件系统

    B->>S: GET / HTTP/1.1
    S->>S: accept + recv 请求头
    S->>S: sscanf 解析 path
    S->>SP: safe_path("/")
    SP->>SP: 拼成 static/index.html
    SP->>FS: realpath 规范化
    FS-->>SP: /home/.../static/index.html
    SP->>SP: 校验是否以 static_root 开头
    SP->>SP: 校验后面紧跟 / 或结束
    SP-->>S: resolved 路径
    S->>FS: open + fstat + 循环 read
    FS-->>S: 文件字节
    S->>S: read_file 关闭 fd
    S->>B: send_response 200 + text/html
    S->>S: close conn_fd
```

**与 POST /infer 的区别**：没有推理、没有数据库，只是"路径校验 → 读文件 → 发出去"。
