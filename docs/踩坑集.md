# 一、构建与环境（7 条）

## 1. ★ `undefined reference to 'main'` —— 第一次真正的链接错误

**现象**
```
/usr/bin/ld: /usr/lib/.../crt1.o: in function `_start':
(.text+0x1b): undefined reference to `main'
collect2: error: ld returned 1 exit status
```

**定位**
1. `ls -l src/main.cpp` → **0 字节**
2. 翻 VSCode 的 Local History，发现内容被写到了**迁移前的旧路径** `~/projects/src/main.cpp`
3. 根因不是"没写 main"，而是**写在了错误的位置**（编辑器还开着旧标签页）

**根因**
编译阶段完全正常（空文件也能编译成空的 `.o`），错误发生在**链接阶段**：链接器在所有 `.o` 里找不到 `main` 这个符号。C++ 的 `main` 是程序入口，**必须由某一个 `.o` 提供**。

**解决**
把内容写到正确路径，并养成"改完 → `Ctrl+S` → `cmake --build` → 看输出"的循环。

## 2. ★ `CMakeList.txt` 少了 s —— 文件名拼错

**现象**
```
CMake Error: The source directory "/home/zrj/projects/imgsvc" does not appear to contain CMakeLists.txt.
```

`ls` 一看：`CMakeList.txt`

**根因**
CMake **硬性要求**文件名是 `CMakeLists.txt`（复数 s），大小写也必须完全一致。这不是约定，是硬编码的查找规则。

**解决**
改名。

## 3. ★ `project(imgsvc c++)` —— 语言标识符写错

**现象**
```
CMake Error: Could not find cmake module file: CMakeDeterminec++Compiler.cmake
CMake Error: CMAKE_c++_COMPILER not set, after EnableLanguage
```

**定位**
报错里的 `CMAKE_c++_COMPILER` 很可疑——正常应该是 `CMAKE_CXX_COMPILER`。

**根因**
CMake 的语言标识符是固定枚举：`C`、`CXX`、`CUDA`、`Fortran`……**`c++` 不是合法值**。它把 `c++` 当成了一个"语言名"，去找 `CMakeDeterminec++Compiler.cmake` 这个模块，自然找不到。

**解决**
`project(imgsvc CXX)`

## 4. ★ `target_link_libraries` 放在 `add_executable` 之前

**现象**
```
CMake Error at CMakeLists.txt:15 (target_link_libraries):
  Cannot specify link libraries for target "imgsvc" which is not built by this project.
```

**定位**
看行号：`target_link_libraries` 在 `add_executable` **上面**

**根因**
CMake 是**顺序执行**的脚本。`target_link_libraries(imgsvc ...)` 的意思是"给**已存在的**目标 imgsvc 加链接库"，但此时 imgsvc 还没被 `add_executable` 创建出来。

**解决**
调整顺序，记住一条规则：**声明 → 设置 → 找库 → 建目标 → 挂属性**

## 5. ★ ONNX Runtime 的 CMake 配置和实际文件布局对不上

**现象**
```
CMake Error: The following variables are used in this project, but they are set to NOTFOUND:
  onnxruntime_LIBRARIES
```
以及 `lib64/libonnxruntime.so.1.30.0` 缺失、`include/onnxruntime` 目录不存在。

**定位**
1. `find /opt/onnxruntime -maxdepth 2 -type d` → 看到实际是 `include/` 和 `lib/`
2. 打开官方 `onnxruntimeConfig.cmake` → 发现它的假设是 `lib64/` 和 `include/onnxruntime/`

**根因**
官方发版 tarball 的 **CMake 配置文件是自动生成的**，它假设的是"标准安装布局"（`lib64/`，头文件在 `include/onnxruntime/`），但实际打包出来的是 `lib/`，头文件直接放在 `include/` 下。**配置文件和二进制不一致。**

**解决**
绕过 `find_package`，手动指定：
```cmake
find_library(ONNXRUNTIME_LIB NAMES onnxruntime PATHS /opt/onnxruntime/lib REQUIRED)
target_include_directories(imgsvc PRIVATE /opt/onnxruntime/include)
target_link_libraries(imgsvc PRIVATE ${ONNXRUNTIME_LIB})
```

## 6. ★ IntelliSense 全红但编译通过 —— VSCode 工作区根目录不对

**现象**
`#include <onnxruntime_cxx_api.h>` 报红波浪线，但 `cmake --build` 完全正常。

**定位**
1. 确认 `build/compile_commands.json` 已生成（`CMAKE_EXPORT_COMPILE_COMMANDS ON`）
2. 打开 VSCode 窗口标题 → 是 `projects [WSL]`，不是 `imgsvc [WSL]`
3. **工作区根目录比项目根目录高了一层**

**根因**
VSCode 的 C/C++ 扩展只会在 `${workspaceFolder}` 及其 `build/` 子目录下找 `compile_commands.json`。工作区开在了父目录 `~/projects`，而文件在 `~/projects/imgsvc/build/`，**差一层就找不到**。

**解决**
```bash
code --remote wsl+Ubuntu-24.04 --reuse-window /home/zrj/projects/imgsvc
```
并设置 `${workspaceFolder}/build/compile_commands.json`。

# 二、C++ / OpenCV（5 条）

## 8. ★ `std::cout << NULL` 让后续所有输出静默消失（踩了 3 次）

**现象**
程序跑完什么都没打印，退出码却是 0。或者只打印了一半就断了。

**定位**
1. 检查所有 `cout << xxx`，找有没有可能传 `NULL` 的
2. 三次分别是：
   - `fgets(buf, ...)` 返回 `NULL`（读文件失败）后直接 `cout << buf`
   - `argv[1]` 越界访问（`argc < 2` 时 `argv[1]` 是 `NULL`）
   - 错误提示字符串里拼了 `argv[1]`

**根因**
`operator<<(const char*)` 遇到空指针时，标准规定设置流的 **`badbit`**。一旦 `badbit` 被设置，**这个流后续的所有输出全部被丢弃**，而且不报错。

**解决**
1. 用之前先判空
2. 或者用 `std::string` 包一层（`std::string(argv[1])`）
3. 关键位置检查 `if (!std::cout) { ... }`

**面试话术**
> "这是我踩得最深的一个坑，**踩了三次**。`cout << NULL` 不崩溃、不报错，只是给流设置 `badbit`，然后**后续所有输出静默消失**。这让我意识到 C++ 输出流的错误处理是'粘性'的——一次失败会污染整个流。**这类'不报错但行为错'的 bug，比崩溃难查得多。**"

## 9. ★ `imread` 失败不抛出、不报错，返回空 `Mat`

**现象**
后续 `cvtColor` / `resize` 全部静默产出空图，最后 `imwrite` 写出一个 0 字节或异常文件。

**定位**
在每一步打印 `img.empty()` 和 `img.cols/img.rows`。

**根因**
OpenCV 遵循 C 风格：**失败返回特殊值**（`imread` 返回空 `Mat`，`imwrite` 返回 `false`），而不是抛异常。

**解决**
**每次 `imread` / `imdecode` 后立刻判空**：
```cpp
cv::Mat img = cv::imread(path, cv::IMREAD_COLOR);
if (img.empty()) { /* 处理失败 */ }
```

**面试话术**
> "C++ 生态里有三种失败通知方式：**返回特殊值**（POSIX / OpenCV：NULL、-1、false）、**抛异常**（STL / ONNX Runtime）、**设置 errno**（系统调用）。所以我每调用一个外部函数，第一件事就是判断它属于哪一种。"

---

## 10. ★ 缩小时用错了插值算法

**现象**
缩小后的图有锯齿/摩尔纹。

**根因**
当时选了 `INTER_NEAREST_EXACT`（因为名字里有"EXACT"，以为更精确）。实际上：
- `INTER_AREA` 才是**缩小的推荐算法**（官方头文件注释："may be preferred for image decimation, as it gives moire'-free results"）
- `_EXACT` 后缀的含义是**位精确 / 与 PIL 一致**，**不是质量更好**

**解决**
- 缩小 → `INTER_AREA`
- 放大 → `INTER_CUBIC` / `INTER_LANCZOS4`

**面试话术**
> "**插值算法要区分放大和缩小**——缩小用 `INTER_AREA`（区域平均，抗摩尔纹），放大用 `INTER_CUBIC`。另外 `_EXACT` 后缀不代表质量更好，它代表位精确。"

## 11. ★ 文件类型 ≠ 扩展名

**现象**
`data/test.jpg` 用 OpenCV 能读，但和 Python 读出来的结果对不上。

**定位**
```bash
file data/test.jpg
# → RIFF (little-endian) data, Web/P image
```

**根因**
这个文件**扩展名是 .jpg，实际是 WebP**。不同解码器对同一份字节的处理可能有细微差异。

**解决**
用 `file` 命令或读 magic bytes 判断真实格式，不要相信扩展名。

**面试话术**
> "扩展名只是命名，**文件类型由开头的 magic bytes 决定**。我用 `file` 命令发现测试图其实是 WebP，这解释了为什么某些情况下 C++ 和 Python 的结果对不上。"

---

## 12. ○ `cv::Mat` 是浅拷贝句柄

**现象**
修改"副本"导致原图也变了。

**根因**
`cv::Mat` 的赋值和拷贝构造都是**浅拷贝**——只复制头部（宽、高、类型、数据指针），**像素数据共享**。引用计数管理生命周期。

**解决**
需要独立数据时用 `.clone()`（深拷贝）或 `.copyTo()`。

**面试话术**
> "`cv::Mat` 本质是一个**带引用计数的智能指针 + 头部信息**。`Mat b = a` 之后两者共享像素内存。这和 C++ 的 `shared_ptr` 语义类似，但 `cv::Mat` 不做写时复制（COW），所以修改会互相影响。"

# 三、模型与推理（6 条）

## 13. ★ 凭感觉写的预处理和模型要求对不上

**现象**
第一次拿到 `.onnx` 模型时，按"分类模型惯例"写了 `224×224` 灰度输入。
后来打印模型接口才发现：
```
输入[0]: input.1  shape=[1,3,320,320]
```

**根因**
**模型的输入规格必须从模型文件里读，不能猜。** 这个模型要 `320×320` 的 **3 通道**（不是灰度）。

**解决**
先写一段"读模型接口"的代码，打印所有输入输出的名字和 shape，再写预处理。

**面试话术**
> "我做的第一件事不是写推理，而是**问模型要什么**——打印出输入输出的名字和形状。结果发现是 `[1,3,320,320]`，而我的代码是按 `224×224` 灰度写的，**差了两个维度**。这让我养成习惯：**接入任何模型前，先把它的 I/O 规格打印出来。**"

## 14. ★ `blobFromImage` 无法表达"每通道不同的标准差"

**现象**
用 `blobFromImage` 做 ImageNet 归一化，结果和标准做法差一点。

**根因**
`blobFromImage` 内部算的是 `(input - mean) * scalefactor`，而 `scalefactor` **只有一个 `double`**。但 ImageNet 的 `std = (0.229, 0.224, 0.225)` 是**每通道不同**的，**一个系数表达不了三个不同的除法**。

**解决**
分两步：
1. `blobFromImage(img, 1.0/255.0, Size(320,320), Scalar(), true, false, CV_32F)` —— 做 resize + BGR→RGB + /255 + HWC→NCHW
2. 手动按通道做 `(x - mean[c]) / std[c]`

**面试话术**
> "`blobFromImage` 能做四件事：resize、换通道、乘系数、HWC→NCHW。但它**做不到标准的 ImageNet 归一化**，因为它的 `scalefactor` 是标量，而标准差是每通道不同的矢量。所以我把归一化拆出来自己做。"

## 15. ★ HWC 和 NCHW 的内存布局

**现象**
搞不清 `blob` 里"第 c 个通道的第 i 个像素"在哪个位置。

**根因**
- **OpenCV 是 HWC（交错）**：`RGBRGBRGB...`，每个像素的 3 个通道挨在一起
- **模型要 NCHW（分平面）**：`RRRR...GGGG...BBBB...`，每个通道的所有像素连续存放

所以下标是 `c * (H*W) + i`。

**面试话术**
> "内存里其实**没有'通道'这个东西**，只有一条连续的 float 数组。'通道'是人为划分的。HWC 是交错存放，NCHW 是分平面存放。**下标公式 `c*HW + i` 就是'跳到第 c 段，再走 i 步'。**"

## 16. ★ 模型的输出名字是 PyTorch 内部张量 ID

**现象**
```
输出个数: 7
输出[0]: 1959  shape=[1,1,320,320]
输出[1]: 1960  ...
```

**根因**
PyTorch 导出 ONNX 时**没有给输出命名**，就直接用了内部张量 ID 当名字。**换个导出环境就变**。

**解决**
用**索引**取输出（`GetOutputNameAllocated(0, alloc)`），不要写死字符串 `"1959"`。

**面试话术**
> "这个模型的输出名字是 `1959`、`1960` 这种数字——因为 PyTorch 导出时没命名，用了内部张量 ID。**结论：不要写死名字，用索引取。** 名字可能变，索引不会。"

## 17. ★ 悬垂指针：`outputs` 析构后内存被释放

**现象**
如果把 `infer()` 写成"返回 `float*`"，函数返回后指针指向已释放的内存。

**根因**
```cpp
float* infer(...) {
    auto outputs = session.Run(...);       // outputs 是局部变量
    float* p = outputs[0].GetTensorMutableData<float>();
    return p;                               // ❌ 指向 outputs 内部内存
}                                           // ← 这里 outputs 析构，内存被释放
```
**"释放"不等于"清零"**，内容往往还在原地 → 指针看起来能用，但随时可能被复用 → **未定义行为**。

**解决**
在函数返回前**把数据拷贝出来**：`mask.assign(p, p + 320*320);`

**面试话术**
> "这是 C++ 最经典的坑之一——**悬垂指针**。最危险的是它**通常不崩溃**，因为内存刚释放时内容还在，测试时看起来完全正常，上线跑久了才偶发错误。我用的是'函数内把结果拷进调用者提供的容器'，从根上避免。"

## 18. ★ 模型常驻 vs 每次重载（3.3 倍差距）

**现象**
命令行版的 `infer()` 是函数，每次调用都构造 `Ort::Session` → **每次重新加载 167 MB 模型**。

**实测**
| 方案 | 每请求 |
|---|---|
| 每次重载模型 | **0.730 秒** |
| 模型常驻（类） | **0.220 秒** |

**解决**
把推理封装成类 `InferEngine`：
- 构造函数里加载模型（程序启动时一次）
- `run()` 只做推理

**面试话术**
> "命令行程序每次调用加载一次模型无所谓，但服务端要处理成百上千个请求。我实测过：**每次重载 0.73 秒/请求，模型常驻 0.22 秒/请求，差 3.3 倍**。所以我把推理从'函数'改成了'类'——模型在构造函数里加载一次、常驻内存。**这个优化的代价是约 1 GB 常驻内存**，做并发时要重新评估。"

## 19. ★ 用张量 min/max 做数值自检

**问题**
预处理写完，怎么知道对不对？不能只靠"看起来像"。

**方法**
ImageNet 归一化的**理论值域**可以精确算出来：

```
min = (0 - 0.485) / 0.229 = -2.118   ← 全黑像素落在 R 通道
max = (1 - 0.406) / 0.225 =  2.640   ← 全白像素落在 B 通道
```

实测 `min=-2.1179 / max=2.6400` —— **精确命中两个端点**。

**这同时证明了四件事**：形状对、缩放对、**通道顺序对**（min 出现在 R 而不是 G/B）、归一化对。

**面试话术**
> "我不想用'看起来对'来验证预处理，所以用了**张量的 min/max 自检**。ImageNet 归一化后理论范围是 [-2.118, 2.640]，实测精确落在这两个端点上。**这个方法不需要肉眼比对图片，还能发现 BGR/RGB 反了这类静默错误**——因为如果通道顺序错了，min/max 会偏离。"

## 20. ○ U²-Net 对风景照失败（模型能力边界）

**现象**
消防栓抠得很好，但栈桥、大桥这类**风景照**几乎全透明。

**定位**
打印掩码统计：

| 图 | 掩码 max | 前景像素 (>0.5) |
|---|---|---|
| 消防栓 | 1.0000 | 16.20% |
| 栈桥 | 0.9997 | 5.59%（只抠到栏杆） |
| **大桥** | **0.0384** | **0.00%** |

**根因**
U²-Net 是**显著目标检测（SOD）**，训练数据是"一张图 + 一个明确的物体"。风景照里**没有单一主体** → 模型判定"没有显著目标"。

**这不是 bug，是模型的任务定义和期望不符。**

**解决（可选方案）**
1. 接受边界，并在文档里说清楚
2. **框选 + 裁剪**：只对用户框内的区域推理 → 框内物体成为唯一显著目标（实测前景占比从 0% → 6.57%）
3. 换模型（SAM / BiRefNet 等）

**面试话术**
> "我用掩码统计验证过：**风景照的掩码最大值只有 0.04，说明模型判定不存在显著目标**，不是我的实现问题。这是**分布外（OOD）**问题——模型只在它见过的数据分布内工作。**我知道我的系统在哪里失效，并且能证明原因**，我认为这比'什么图都能抠'更可信。"

# 四、网络与 HTTP（8 条）

## 21. ★ `send` 长度硬编码，截断在一个汉字中间

**现象**
客户端收到乱码 `服务端：消息已收到` 变成 `服务端：消�`。

**定位**
用 `xxd` 看响应的原始字节：
```
e69c 8de5 8aa1 e7ab afef bc9a e6b6 88e6
                                       ↑ 只有半个汉字（e6 是 3 字节序列的第 1 个）
```
字节数 **16**，但 `printf '服务端：消息已收到' | wc -c` = **27**。

**根因**
手写 `send(fd, msg, 16, 0)`，**16 是硬编码的**。中文字符在 UTF-8 里占 3 字节，9 个字符 = 27 字节。

**解决**
用 `strlen(msg)` 算长度。

**面试话术**
> "我犯过一个错：`send` 的长度写死成 16，但中文字符串实际是 27 字节，结果**截断在一个汉字中间**，产生非法 UTF-8。**TCP 层面只认字节，长度必须精确计算，而且要区分'字符数'和'字节数'。**"

## 22. ★ 没处理 SIGPIPE → 进程静默死亡

**现象**
服务器偶尔"人间蒸发"，没有任何日志、没有 core dump。

**根因**
客户端发完请求**立刻关闭连接**，服务器这时才 `send` 回复 → 内核给进程发 **`SIGPIPE`** → **默认动作是终止进程**。

它**不返回 -1**，是直接发信号——所以你的错误处理代码根本没机会执行。

**解决**
```cpp
send(fd, data, len, MSG_NOSIGNAL);   // 只影响这次 send（推荐）
// 或 signal(SIGPIPE, SIG_IGN);      // 全局忽略
```

**面试话术**
> "`SIGPIPE` 是我遇到的最阴险的坑——**服务器不报错、不崩溃，就是直接消失**。原因是往一个已关闭的连接写数据，内核发 `SIGPIPE`，默认动作是终止进程。这类'进程被信号杀掉'的问题，**光看程序日志是查不到的**，必须知道信号机制。"

## 23. ★ 日志用 `printf` 到 stdout，进程被杀时全丢

**现象**
服务器跑了 4 个连接，日志文件里 **0 字节**。

**根因**
| 输出目标 | 缓冲方式 |
|---|---|
| stdout → 终端 | 行缓冲（遇 `\n` 刷新） |
| **stdout → 文件/管道** | **全缓冲（4 KB 才刷）** |
| **stderr** | **无缓冲，立刻写出** |

服务器被重定向到文件（或 systemd 接管）→ 全缓冲 → 进程被 kill 时缓冲区里的内容**直接丢弃**。

**解决**
日志改用 `fprintf(stderr, ...)`。这同时符合 Unix 惯例（stdout 输出数据、stderr 输出日志）。

**面试话术**
> "这个坑的后果很严重：**服务器崩溃时，最后几条日志（往往最关键的那些）恰好丢了**。因为 stdout 重定向到文件时是全缓冲。改用 `stderr` 既解决了缓冲问题，也符合 Unix 惯例。"

## 24. ★ `recv` 一次收不完（短读）→ 必须按 Content-Length 循环

**现象**
本地测试 `hello socket` 完全正常，所以以为不用循环。

**真相**
TCP 是**字节流**，`recv` 只保证"给你一部分，至少 1 字节"，**不保证给全部**。

**解决**
1. 先收到完整的**请求头**（循环直到找到 `\r\n\r\n`）
2. 解析 `Content-Length`
3. **计算已经收到多少 body**（第一次 recv 可能把头 + 一部分 body 一起收到了）
4. 循环 `recv` 直到收满

**实测**
5 MB 随机二进制数据**逐字节完整往返一致**。

**面试话术**
> "TCP 没有'消息边界'这个概念，它是字节流。所以接收方必须自己分帧——HTTP 用 `Content-Length` 来分帧。我这里有个容易漏的细节：**第一次 `recv` 可能已经把一部分 body 收进来了**，所以不是'从头开始收 body'，而是'算出已经收了多少、还差多少'。"

## 25. ★ `send` 也会短写 → 大响应发不完

**现象**
发大文件（几百 KB）时，客户端收到的图片残缺。

**根因**
`send` 的返回值是**实际发出去的字节数**。内核 socket 发送缓冲区满了就只发一部分。

**解决**
循环：
```cpp
size_t sent = 0;
while (sent < len) {
    ssize_t n = send(fd, p + sent, len - sent, MSG_NOSIGNAL);
    if (n <= 0) break;
    sent += n;
}
```

**面试话术**
> "**`send` 短写和 `recv` 短读是一对**——都是'部分完成'语义，必须循环。而且层次要分清：**`send` 短写是 TCP 层的问题，`Content-Length` 分帧是 HTTP 层的问题**，两个层次都要处理。"

## 26. ★ `Content-Length` 必须是字节数

**现象**
页面上的中文显示不全，或者客户端一直转圈等剩下的字节。

**根因**
`Content-Length` 声明的是 **body 的字节数**。如果 body 里有中文（3 字节/字），用"字符数"就会写小 → 客户端等不到足够的字节，直到超时。

**解决**
用 `strlen(body)` 或 `body.size()`，并用 `curl -v` 和 `wc -c` 交叉验证。

**面试话术**
> "`Content-Length` 是 HTTP 层的分帧依据，**写错的后果是'客户端一直等'**。写大了会等到超时，写小了会把剩余的字节当成下一个响应的开头（在 keep-alive 下）。"

## 27. ○ 请求头超过缓冲区 → 静默截断

**现象**
请求头超过 `BUF_SIZE` 时，后面的字节被丢弃，用残缺数据解析。

**解决**
1. 缓冲区要够大（我用 `malloc(10 MB)`，只分配一次、每个连接复用）
2. **超长要明确拒绝**（返回 413 或 431），而不是静默截断

**面试话术**
> "**静默截断比报错更危险**——数据看起来收到了，但不完整。我的做法是：超过上限就返回 413，让客户端知道，而不是假装收完了。"

## 28. ○ 路径穿越：`static/../src/server.cpp`

**现象**
如果按请求路径拼文件名，`GET /../src/server.cpp` 会让服务器**吐出自己的源码**。

**原理**
```
用户请求      /../src/server.cpp
    ↓ 拼上 static
文件路径      static/../src/server.cpp
    ↓ 操作系统解析（.. = 回上一级）
实际打开      src/server.cpp
```
往上穿 5 层就到 `/`，能读 `/etc/passwd`。

**错误做法**
黑名单（拒绝含 `..` 的路径）——**永远有绕过方法**（`%2e%2e`、`....//`、符号链接）。

**正确做法**
```cpp
// 1. realpath 规范化成绝对路径（解析掉所有 ../ 和符号链接）
// 2. 检查它是否还在 static 目录里面
if (strncmp(resolved, static_root, root_len) != 0) return false;
// 3. ★ 前缀校验的陷阱：后面必须紧跟 '/' 或结束
//    否则 static_bak/xxx 也会被判为"以 static 开头"
if (resolved[root_len] != '\0' && resolved[root_len] != '/') return false;
```

**★ 一个重要的注意点**：加了 URL 解码之后，`%2f` 会变成真正的 `/`，**必须重新跑一遍攻击测试**。

**面试话术**
> "路径穿越我用的不是黑名单，而是**先规范化、再校验前缀**。因为黑名单永远有绕过方法。**而且前缀校验有个经典陷阱：`static_bak/` 也以 `static` 开头**，所以必须确认后面紧跟 `/` 或字符串结束。"

## 29. ○ SQL 注入：OR 注入让条件永远为真

**现象（实测）**
```sql
-- 攻击者输入：  ' OR '1'='1' -- 
-- 拼进 SQL 后：
SELECT id, name FROM t WHERE name = '' OR '1'='1' -- ';
→ 返回全部 3 行（本该只返回 1 行）
```

**根因**
**数据和代码混在一起** —— 用户输入被当成 SQL 语法解释了。

**解决**
```cpp
mysql_real_escape_string(c, esc, user_input, len);
// 把 ' 转义成 \'，让攻击者跑不出字符串边界
```
**更彻底**：预编译语句（`mysql_stmt_prepare` + 参数绑定）。

**关于 `; DROP TABLE`**
很多人以为"没开多语句支持就安全"——**错**。没开多语句时，`DROP` 不执行，但整条 SQL 会**语法错误**，数据写不进去（也是故障）。**这只是把"表被删"降级成"写入失败"，不是安全。**

**面试话术**
> "注入的本质是**数据和代码混在一起**。防护有两条路：**转义**（给数据戴手铐）和我认为更彻底的**预编译语句**（把数据通道和代码通道彻底分开）。我用了转义，因为它简单够用；但生产系统我会换成预编译。"

## 30. ★ 中文入库乱码 → 字符集没对齐

**现象**
`消防栓.jpg` 入库后变乱码。

**根因**
连接字符集和表的字符集不一致。**要五层全部 `utf8mb4`**：
```
服务端 → 数据库 → 表 → 连接会话 → 代码里 mysql_set_character_set
```

**解决**
```cpp
mysql_set_character_set(c, "utf8mb4");
```

**面试话术**
> "字符集要**端到端对齐**，任何一层不一致都会乱码。我的做法是五层全部 `utf8mb4`，并在连接时显式设置。"

## 31. ★ 连接会被服务端悄悄断开 → 必须 ping 重连

**现象**
服务跑了一夜，第二天第一个请求报 `MySQL server has gone away`（错误 2006）。

**根因**
MySQL 的 `wait_timeout`（默认 **28800 秒 = 8 小时**）会把空闲连接**服务端单方面断开**，而客户端还以为是连着的。

**解决**
每次操作前 `mysql_ping`，断了就**关掉旧的 + 重新 init + 重新 connect**：
```cpp
if (mysql_ping(conn) != 0) {
    mysql_close(conn); conn = nullptr;
    conn = mysql_init(nullptr);
    mysql_real_connect(...);
    mysql_set_character_set(conn, "utf8mb4");   // 重连后要重设
}
```
**实测验证**：用另一个会话 `KILL` 掉连接，程序正确打印"连接已失效，正在重连 → 重连成功"。

**面试话术**
> "长连接复用是标准做法，但 **MySQL 有 `wait_timeout`，空闲会被服务端单方面断开**。所以我在每次操作前用 `mysql_ping` 检查。注意**重连后字符集可能被重置，要重新设一次**；而且**重连会丢失会话状态**（临时表、事务），我的代码不用这些所以没问题。"

## 32. ○ `mysql_free_result` 忘了调 → 每次查询泄漏内存

**现象**
不调的话每次查询泄漏一块内存。

**根因**
`mysql_store_result` 把整个结果集**拷贝到客户端内存**，必须手动释放。

**解决**
```cpp
MYSQL_RES* res = mysql_store_result(c);
while ((row = mysql_fetch_row(res))) { ... }
mysql_free_result(res);   // ★ 必须
```

**面试话术**
> "MySQL C API 是 C 风格，**没有 RAII，所有资源都要手动释放**。`mysql_free_result` 漏掉的后果是每查询泄漏一次——1 万次请求后可能 OOM。"

## 33. ○ 索引的收益与代价（实测数据）

**实测（10 万行、数据全在内存）**

| 场景 | 无索引 | 有索引 | 倍数 |
|---|---|---|---|
| 按 `h` 精确查 | 8.15 ms | 0.30 ms | **27×** |
| 按 `cost` 排序取 20 | 9.81 ms | 0.077 ms | **128×** |

`EXPLAIN` 的 `rows` 从 **99994 → 1 / 20**。

**代价（也实测了）**
```
ALTER TABLE ADD INDEX idx_h    → 5.19 秒（10 万行）
ALTER TABLE ADD INDEX idx_cost → 1.14 秒
```
而且**每次 INSERT 都要同步更新所有索引**。

**面试话术**
> "我在 10 万行、数据全在内存的条件下实测，索引让按哈希查找从 8ms 降到 0.3ms（27 倍）。**但数据量大到内存放不下时差距会更大**，因为全表扫描要读磁盘。同时我也实测了索引的代价：建一个索引 10 万行要 5 秒，而且写入变慢。**所以只给 WHERE / ORDER BY 里经常出现的列建索引。**"

## 34. ★ `char(64)` vs `varchar(255)`

**答案**
| 类型 | 占用 | 适用 |
|---|---|---|
| `char(N)` | **固定 N 字节**（不足补空格） | 长度完全固定：SHA-256（64 字符）、MD5、身份证号 |
| `varchar(N)` | **按实际长度**（+长度信息） | 长度不定：文件名、用户名 |

**为什么表里一个用一个**
- `image_hash` 永远是 64 个十六进制字符 → `char(64)`
- `image_name` 可能 5 字符也可能很长 → `varchar(255)`

**面试话术**
> "`char` 定长、`varchar` 变长。SHA-256 长度固定所以用 `char(64)`，不存长度信息；文件名长度不定所以用 `varchar`，避免短文件名也占满 255 字节。"

# 附：这个项目里"两种错误通知方式"的对照

**C++ 生态里的两种风格，必须分清：**

| 风格 | 代表 | 怎么报错 | 你要做什么 |
|---|---|---|---|
| **C 风格** | MySQL C API、POSIX（`open`/`recv`/`send`）、OpenCV | **返回特殊值**（NULL / -1 / 非 0 / false），配 `errno` 或 `mysql_error` | 每次调用后**立刻判断返回值** |
| **C++ 风格** | ONNX Runtime（`Ort::Exception`）、STL（`std::bad_alloc`） | **抛异常** | 用 `try/catch` 包起来 |

**我的项目里两种都有：**
- `Ort::Session` 构造要 `try/catch`
- `mysql_query`、`recv`、`send`、`imread` 都要看返回值

**面试话术**
> "我一开始在 MySQL 的代码上写了 `try/catch`，后来发现它根本不会抛异常——C API 是通过返回值报错的。**这让我意识到'怎么知道它失败了'必须按库来分**，不能凭习惯。"
